# Mobile release

ProofScan uses Expo SDK 58. The mobile app loads the same workspace as the web and desktop apps. **Scan device** opens the native React Native flow for consent, camera capture, device readings, report review and the seller’s sharing decision. **Privacy** explains the scanner’s data use and opens the deployed privacy and account-deletion pages.

## Build profiles

| EAS profile | Distribution | Android | iOS |
| --- | --- | --- | --- |
| `development` | Internal | Development client using Metro | Development client on a provisioned device |
| `preview` | Internal | Standalone APK | Ad hoc build on registered devices |
| `production` | Store | Android App Bundle | App Store archive |

All EAS commands run from `apps/mobile`. Connect the directory to the intended Expo organization and project with `npx eas-cli@latest init`. If EAS asks you to add a project ID manually because the project uses a dynamic config, put the actual EAS project ID under `expo.extra.eas.projectId` in `app.json`. Both release profiles use the same app identifiers. A preview install can replace or conflict with an installed store build, depending on the platform and signing. [Expo monorepo setup](https://docs.expo.dev/build-reference/build-with-monorepos/) · [EAS profiles](https://docs.expo.dev/build/eas-json/)

Configure these public variables in both the EAS **preview** and **production** environments. Set the preview variables to the staging deployment when available. Each value is readable from the app bundle.

| Variable | Value |
| --- | --- |
| `EXPO_PUBLIC_PROOFSCAN_ORIGIN` | The HTTPS workspace origin, matching the deployed API’s `WEB_ORIGIN`. Route `/api/v1` through the same origin. |
| `EXPO_PUBLIC_PROOFSCAN_PRIVACY_URL` | A public HTTPS page for the release privacy policy. |
| `EXPO_PUBLIC_PROOFSCAN_DELETE_ACCOUNT_URL` | A publicly reachable HTTPS entry point where an account holder can authenticate and initiate deletion. |

The configuration rejects missing URLs and cleartext HTTP in the release profiles. Keep database credentials, report signing keys, Moonshot keys and privileged Supabase credentials on the server. EAS draws from the monorepo and uses the repository’s Git ignore rules for its build archive. Native projects generated by Expo, local MCP configuration, signing material and private environment files are ignored. [EAS environment variables](https://docs.expo.dev/eas/environment-variables/) · [EAS build archives](https://docs.expo.dev/build-reference/easignore/)

After project linking and access to the appropriate signing accounts:

```sh
cd apps/mobile
npx eas-cli@latest build --platform android --profile preview
npx eas-cli@latest build --platform ios --profile preview
npx eas-cli@latest build --platform all --profile production
```

Run the first two commands before attempting the store builds. The native splash must be checked with a standalone release-style build. Expo Go and development clients can show a different launch screen. [Expo splash screen](https://docs.expo.dev/develop/user-interface/splash-screen-and-app-icon/)

## Release checks

- On physical Android and iOS devices, check the launcher icon, cold launch, foreground recovery, safe areas, text scaling, VoiceOver or TalkBack, and the Android back button. Disable the network before opening the app, then verify that **Try again** recovers once the network returns.
- Sign in and out of the shared workspace, open a report and verify that ordinary same-origin navigation works. Test against the production authentication configuration. If authentication uses another origin, verify an explicitly supported system-browser sign-in and callback before release.
- Create a seller link from the workspace. Paste it into the scanner, decline camera access, and complete verification using device readings alone. Repeat with access granted and each photo angle, including cancel, retake and permanent camera denial. Check screen rotation and app backgrounding while the system camera is open.
- Reopen the app and resume a saved seller session. Verify an expired or revoked link prompts for a fresh link. Forget the saved session and reopen the app to confirm it was removed.
- Compare the preview and the buyer’s signed report. Run separate share and decline flows and verify that the buyer can only access the shared report. Check that a timed-out share can reconcile against the saved server decision.
- Run the workflow with demo data on the actual review build. Prepare a reviewer account and a functioning seller link. Describe the native camera and hardware collector in the App Review notes. Reviewers evaluate the app’s native functionality and the entire workspace. [App Review Guidelines](https://developer.apple.com/app-store/review/guidelines/)

## Store and operational requirements

- Link the Expo project and configure Google Play and Apple signing. Verify the Android target API and the iOS build toolchain against the submission rules for the release date. Use a signed preview build on each platform before submission.
- Set `EXPO_PUBLIC_PROOFSCAN_DELETE_ACCOUNT_URL` to the deployed `/account/delete` page. Verify deletion with a test account from the app and a standalone browser. Check that the hosted identity is deleted by the worker, and publish the privacy policy and backup retention window before opening public registrations. [Apple account deletion](https://developer.apple.com/support/offering-account-deletion-in-your-app/) · [Google Play account deletion](https://support.google.com/googleplay/android-developer/answer/13327111)
- Complete the actual store disclosures from the deployed data flow. This includes account and verification data, device manufacturer/model/memory, optional exterior photos, retention and deletion behavior, reviewer access, and third-party processors enabled on the backend. Inspect the iOS archive’s dependency privacy manifests and review the export compliance questionnaire. Add store screenshots, app descriptions, ratings, the privacy URL and the support contact for the release. [Expo privacy manifests](https://docs.expo.dev/guides/apple-privacy/) · [Google Play data safety](https://support.google.com/googleplay/android-developer/answer/10787469)
- Monitor the production workspace and API alongside store crash and startup reports. Keep private links, access tokens, device photos and report payloads out of logs and telemetry. Configure a staged rollout and use the last verified release as a recovery point.

CI runs Expo Doctor, the release URL and profile tests, the mobile type check, and production JavaScript exports for both platforms using reserved fixture URLs. Those checks require neither project linking nor signing. Signed builds, store review and physical device acceptance are tracked separately from those repository checks.
