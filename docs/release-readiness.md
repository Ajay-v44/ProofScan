# ProofScan release review

## Release decision

The repository is ready for controlled acceptance testing of purchase verification, pickup rechecks, handoffs, and Buyer Chat. Public signup and store submission need the release gates below. Evaluate web, each native scanner, and the hosted backend separately.

| Area | What the review found | Release decision |
| --- | --- | --- |
| API and persistence | Async request handling, typed contracts, explicit owner checks, state transitions, and database-backed integration tests provide a solid base. Verification and handoff modules still combine endpoint logic, workflow transitions, and evidence persistence. | Keep transaction boundaries explicit when changing these modules. Split a service when a second caller needs the same behavior. Measure migration lock times and test recovery on a staging copy. |
| Web workspace | The main workflows were present. Workspace tools switched to unrelated page layouts, the phone navigation could overflow, and the brand used a generic scanner icon. | The overview, reports, handoffs, and Buyer Chat share a layout. Phone navigation keeps four primary destinations visible, and secondary tools are reachable from Workspace options. The branded seller and camera pages keep each task focused. Verify keyboard, zoom, and screen-reader use on the deployed version. |
| Android and iOS | Expo shares the responsive browser workspace and uses the same brand assets and palette in native screens. The scanner uses a second device for front and back photos. The OS exposes a narrower set of readings than the Windows collector. | Test two-device capture with signed Android and iOS builds. Include iPad, rotation, large text, sharing, permissions, interruptions, and upgrades on physical devices. Display unavailable readings as unavailable. |
| Windows and macOS | The Tauri UI and platform collectors intentionally keep local hardware reads apart from shared web workflows. The Windows CIM flow has browser coverage. macOS runtime behavior and signed installers still need acceptance. | The CI matrix now covers both platforms. Verify macOS native collection, signed and notarized installers, and clean-machine installation before offering downloads. |
| Buyer Chat and guided collection | Owner scope and eligibility are enforced before ranking. Optional model calls previously supplied ungrounded answer text and took a call before sources were available. Vector outages could make the chat unusable. | Retrieval runs first. The app validates model-selected actions, generates explanations from retrieved facts, and falls back to text search if embeddings are unavailable. Keep physical inspection and the seller’s share decision in the workflow. Maintain a small evaluation corpus for ranking, missing or contradictory evidence, stale sources, privacy, and tool failure. [OWASP on misinformation](https://genai.owasp.org/llmrisk/llm092025-misinformation/) |
| Operations and data access | The API separates liveness from database readiness. The operator dashboard tracks aggregate agent volume and cost inputs. Backups, access controls, and alerts depend on a configured environment. | Deploy with the production settings and prove migration, restore, rotation of signing keys, retention jobs, and alert delivery. Put independent ingress abuse limits in front of login, registration, guest links and media uploads. Document response owners for incidents. |

## Public launch gates

1. **Account lifecycle.** Configure hosted authentication and test registration, email verification, session expiry, recovery and operator access. Implement and test account deletion through an authenticated path, including revocation of seller and camera links and removal of associated data under the published retention policy. Decide how signed reports, audit artifacts and backups are handled before publishing that policy. The app’s existing link must lead to a working deletion flow. [Apple account deletion](https://developer.apple.com/support/offering-account-deletion-in-your-app/) · [Google Play user data](https://support.google.com/googleplay/android-developer/answer/10144311)
2. **Staging and operations.** Use representative staging data to verify an upgrade to the current Alembic head, an encrypted backup restore and the rollout plan. Check cross-account access through the deployed proxy. Exercise ingress limits, monitoring for API errors and worker delay, quota alerts, and photo retention. Record request latency and CPU, database and storage use under expected upload and chat traffic before choosing limits.
3. **Real-device and usability acceptance.** Walk through the original seller link, second-camera capture, reading submission, report sharing, and buyer pickup on desktop and physical mobile devices. Use a representative photo set for lighting, alignment, wear and swaps. Verify keyboard focus, reflow, touch controls, visible status and error recovery. Treat visual results as evidence for inspection and report signatures as confirmation of report integrity. [WCAG 2.2](https://www.w3.org/TR/WCAG22/)
4. **Signed distribution.** Build and sign Android, iOS, and desktop packages. Test install and upgrade through TestFlight, Google Play internal testing and the chosen desktop distribution path. Publish privacy disclosures based on the actual data flows. CI bundle exports and native compiler checks cover separate parts of this process. [Expo production builds](https://docs.expo.dev/deploy/build-project/)
5. **Support and product scope.** Publish buyer and seller help for missing readings, failed photos, expired links and a disputed report. Set up support intake and ownership. Describe identity and condition checks as comparison of captured evidence until independent device attestation and broader image validation are available.

## Engineering follow-through

- Keep ownership checks, state changes, and writes under one transaction wherever they govern the same action. Keep model requests and embedding work outside long-lived database locks. Maintain migration tests for a clean database and data from before the latest schema change.
- Generate or contract-test the portions of the TypeScript API types that duplicate FastAPI schemas, particularly error responses and signed report versions. Keep signature canonicalization and compatibility tests when adding fields to signed payloads.
- Move vector generation off the request path if measured first-query latency warrants it. Keep access filters and citation version checks in the database, and compare recall with the exact owner-scoped query before adding an approximate index.
- Add automated accessibility checks and measure layout and performance on the release origins. The browser regression tests exercise the revised chat at phone width. Physical-device camera and assistive technology checks remain separate.
- Prefer a limited web and Windows beta until the account lifecycle, operations and native distribution gates have evidence. Keep mobile and desktop downloads gated by their own install and update checks.
